UE PerfectWorld 是给 **Codex** 使用的 Unreal Engine 项目工作流插件，面向 UE5 的 C++、蓝图及两者协作场景。**多子代理协作是核心执行模块**：主代理负责范围、拆分、关键路径和整合，将可分离的查证、实现、验证与独立审查交给子代理，在授权范围内连续推进。

| 核心部分 | 负责什么 | 如何配合 |
| --- | --- | --- |
| 多子代理执行模块 | 谁负责、哪些工作并行、怎样整合和复审 | 主代理持续推进；子代理按边界交付证据、改动或审查发现 |
| S0-S6 证据检查点 | 需求、证据、规格、实现、验证、评审与交付是否成立 | 随工作推进覆盖；可合并记录，保留真实依赖与授权边界 |
| 保守实现与 UE 专项规则 | 改动是否必要，契约、生命周期和权威侧是否正确 | 优先复用、配置或局部修复，对新增机制说明必要性 |

执行模块由现有技能和公共规则承载。**检查点与代理角色分别组织**：S0-S6 不要求配置七个代理；同一个子代理可以在明确交接后承担下一项有界任务。

**它不是 Unreal Editor 扩展，也不包含 RAG 服务或索引器。** 插件不会因为安装就自动扫描或修改 UE 项目；项目文件仍按当前任务的授权和 S0-S6 证据检查点处理。

<a id="workflow-comparison"></a>
## 用插件和不用插件，差在哪？

普通 Codex 对话也可以完成 UE 开发任务。区别不是“一个会写代码、另一个不会”，而是这些项目检查和过程约束是否被预先定义、持续执行，并留下可以复核的产物。

<p align="center">
  <img src="assets/workflow-comparison.svg" alt="普通 Codex 对话与 UE PerfectWorld 工作方式对照图：主代理统筹多个子代理并行工作，执行层与证据检查配合，并对最新版完成修复、复验和独立复审" width="100%">
</p>

在插件技能已加载并适用于当前任务时，UE PerfectWorld 会把容易遗漏的检查变成默认流程。它不是保证代码正确的自动化工具，而是减少每轮重复说明、让关键检查和未验证事项更容易被看见。对很小的任务，可以缩短或合并检查点的说明；明确的实现或修复请求覆盖了有界改动范围时，可以在同一轮完成查证、规格、实现、验证与评审，不需要每个阶段都停下来确认。

<a id="plugin-framework"></a>
## 插件框架由什么组成

插件框架同时包含执行组织、质量流程与 UE 工程约束。主代理与子代理决定工作怎样分配和推进；S0-S6 检查必要证据；保守实现和 UE 专项规则约束改动内容。

<p align="center">
  <img src="assets/framework-map.svg" alt="UE PerfectWorld 框架图：任务路由、项目证据和 UE 规则之上，独立的多子代理执行模块负责拆分、并行、整合与修复复审，S0-S6 检查点贯穿交付" width="100%">
</p>

图中的层次不是额外的审批阶段，而是同一项 UE 工作在进入实现前后需要经过的项目检查和代码约束。下面逐层展开说明。

### 1. 按任务类型分流，不把所有请求当成“写代码”

插件为不同工作定义了不同入口：只要求诊断已有症状时只读排查；规划、方案或明确“不改文件”的请求保持只读；已有改动交给审查技能。明确要求实现或修复时，先查证并说明紧凑范围与规格，再在授权范围内完成改动。蓝图协作和开发文档则在需要时作为专门能力参与。

这样可以减少两类常见错位：用户只想知道根因，回答却直接改文件；或者用户需要审查现有改动，回答却重新设计整套方案。每个技能都说明了它应该做什么、何时停止、哪些工作不属于它。

```text
                         +-- 已有症状 / 报错 --> 只读排查 --> 根因与证据
                         |
用户提出 UE 任务 --> 判断任务类型 +-- 需求不明确 --> 整理范围 --> 逐文件规格
                         |
                         +-- 已有代码改动 --> 独立审查 --> 问题与风险
                         |
                         +-- 明确实现 / 修复 --> 紧凑范围与规格 --> 有界实现、验证与评审

                    蓝图协作 / 开发文档按需接入
```

### 2. 结论必须落回当前项目证据

插件要求先从当前工作区寻找真实的类、调用方、配置和资产引用，再讨论 UE 项目应该怎样改。证据会尽量落实到 `path:line`；如果关键代码、蓝图资产或运行信息当前不可见，就报告具体缺口，而不是凭通用 UE 经验补出项目事实。

它也不会把“搜到一个相似类”当作可直接照搬的先例。需要比较它是否仍在使用、职责是否相同，以及所有权、生命周期和网络边界是否匹配。对跨系统需求，还要分别追清数据来源、触发、读取、持久化和清理。

```text
UE 项目问题
   |
   +--> 源码：类、实现、活动调用方
   +--> 配置：设置、表格、DataAsset
   +--> 资产：蓝图、组件、资源引用
   +--> 生命周期：创建、使用、持久化、清理
   |
   v
找到当前项目的直接证据？
   +-- 是 --> 记录 path:line --> 核对先例是否仍在用、职责是否匹配
   |
   +-- 否 --> 报告具体证据缺口，不用通用经验补成项目事实
                            |
                            v
                    基于证据形成结论
```

### 3. 先确认项目里谁负责，再决定把逻辑放哪

UE 功能经常横跨 C++、蓝图、DataAsset/DataTable、Subsystem 或共享组件。插件要求先画清责任和生命周期：谁创建状态、谁拥有状态、谁读取或消费、谁负责持久化、谁处理客户端与服务器边界、结束时由谁清理。

如果改动碰到共享组件、公共 API、对象池或异步资源流程，还要检查原有调用方与新调用方是否满足同一契约，包括初始化时机、缓存命中、失败、取消、复用和晚到回调。一次性异步完成通常应沿用事件、回调或项目既有通知，不默认用每帧 Tick 等待。

生产代码优先复用现有能力、调整配置或做局部有界修复。新增机制前，要用项目证据说明这些选项为什么不足；不为单个需求顺手增加管理器、注册表、镜像状态或通用框架。确需扩展时，保持改动与职责、生命周期及当前需求相称。

```text
数据来源 --> 触发者 --> 状态创建者 --> 状态所有者 --> 读取 / 消费者
   |           |            |              |                  |
   +-----------+------------+--------------+------------------+
                                核对
                                 |
                 +---------------+----------------+
                 |               |                |
             谁来持久化？   客户端 / 服务端？   结束时谁清理？

异步 / 共享流程：
初始化 --> 缓存命中 / 未命中 --> 成功 / 失败 --> 取消 / 复用
                                  |
                                  v
                         晚到回调如何处理？
```

### 4. 写代码前做 UE 符号与接口查证

对将要直接写入工程或交付粘贴的代码，插件增加了专门的贴码门禁：检查新增符号是否冲突，确认既有成员的声明和可见性，从实现而不只是函数签名核实参数语义，并在同一模块寻找 include 写法先例。

改动规格会指出目标文件、落点和必要验证；实现阶段按已授权范围小步修改。规格可以紧凑地随进度说明，不必为每个检查点另开一轮批准。交付前还要检查改名或删除的符号是否仍有引用，避免只给出“看起来合理”但实际无法编译或与项目契约不符的代码。

代码注释按项目约定追踪来源：每次任务首次需要新增或修改注释、标记时，先确认作者，再用该作者的 `begin/end` 标记包住实际改动；标记说明保持一行，不扩到未改代码或他人的注释区间。逻辑注释默认单行，只解释新增或实质改动中不明显的步骤。

```text
待写代码
   |
   v
核对目标文件、落点与授权范围
   |
   v
查符号冲突、成员声明 / 可见性、函数实现中的参数语义
   |
   v
确认同模块 include 先例与调用契约
   |
   v
当前请求是否授权这个有界改动？
   +-- 否 --> 保持只读，给出具体规格和待决策事项
   |
   +-- 是 --> 按范围小步修改 --> 检查残余引用 --> 验证与评审
```

<a id="parallel-execution"></a>
### 5. 多子代理执行模块：主代理统筹，子代理并行推进

规模较大且可分离的任务，尽早拆给子代理。主代理明确目标、最新需求、禁止触碰的范围、文件归属、接口和交付证据，并持续处理关键路径。子代理返回具体文件、事实、改动或问题；主代理负责核实、整合及后续调度。

| 角色 | 有界任务 | 返回结果 |
| --- | --- | --- |
| 主代理 | 拆分、协调接口、推进关键路径、整合改动、处理真实决策 | 当前范围、整合版本及最终交付状态 |
| 查证子代理 | 分别追踪调用链、资产配置、生命周期或相关先例 | 可定位的证据、能力缺口和假设冲突 |
| 实施子代理 | 修改明确归属的文件或模块，优先复用现有能力 | 小而完整的改动、影响范围及自检结果 |
| 验证子代理 | 对已稳定部分执行有授权的检查 | 实际结果、失败证据及未验证项 |
| 独立审查子代理 | 按需求和真实差异检查正确性、契约及不必要增长 | 按严重度排列的问题、依据及复审结论 |

这些是按任务选用的职责，不要求同时配齐固定角色。查证可以先并行；依赖证据和接口明确后，再让不同实施者修改各自文件。稳定部分可以提前验证或审查，最终结论仍需覆盖最新整合版本。

执行时保留三个关键约束：

- **每个文件、资产和共享资源同一时间只有一个写入者。** 共享接口先对齐，重叠修改先交接；构建和共享编辑器由单一负责人操作。
- **独立审查依据真实差异和证据。** 实施者的自审不能充作独立复审；多个代理意见一致也不能代替运行验证。
- **修正后形成完整回环。** 确认发现 → 授权范围内修复 → 受影响检查重跑 → 独立审查最新版。没有新证据或进展的反复修补，应回溯契约并报告具体阻塞。

并发数量按当前运行时、配置、工具可用性和实际工作量调整。运行 `ue-setup` 初始化时，默认将 Codex 的子代理并发上限设为 12（不包含主代理），并读回核验；用户指定其他数量时沿用该数量。只检查配置或普通 UE 开发任务不会修改并发设置，实际调度仍受运行时容量限制，不要求填满全部槽位。

小而紧密的改动可直接完成；没有可用子代理时继续本地查证与验证，并说明审查独立性的限制。

### 6. 把验证与评审分开，准确表达“验证到了哪”

验证不是一句“应该可以”。插件要求先列出要检查的路径和预期结果，再运行当前环境能做的检查。结果要区分源码追踪、编译、PIE、自动化、网络模式和打包验证；只在编辑器里看过，不会表述成打包版或服务器行为也已通过。

随后由独立评审者按 `ue-review` 检查需求是否符合、是否破坏项目一致性或生命周期、是否引入不必要的结构。共享资源、取消流程、异步回调和旧路径交界等风险，会按任务相关性进行针对性审查。明确的实现或修复任务中，主代理可修复已授权范围内的审查问题，再复验并让评审者重读最新整合版本；单独的审查请求仍保持只读。没有实际运行的验证会明确列出，不用静态分析冒充运行结果。

```text
                         实际改动
                       /          \
                      v            v
                 验证轨道        独立评审轨道
          路径 + 预期结果       需求 + 一致性 + 风险
                 |                    |
      源码 / 编译 / PIE       生命周期 / 异步 / 共享资源
      自动化 / 网络 / 打包     旧路径 / 不必要结构
                 |                    |
                 +---------+----------+
                           v
                  范围内修复 → 复验与复审
                           |
                           v
                         交付记录
              已验证 / 未验证 / 审查发现
```

### 7. 交付给下一个接手的人，而不只交付给当前对话

完成改动后，插件可整理开发文档与交接信息：改了哪些文件、改动依据是什么、哪些既有路径保持不变、执行了哪些验证、哪些事项仍未验证。文档以实际代码和测试结果为依据，不根据方案猜测最终实现。

授权范围内的工作持续推进，只有未解决的真实决策、范围扩张或尚未授权的构建、外部写入及版本控制操作才需要停下确认。文件编辑授权不自动包含这些额外操作；插件不会自动提交或推送。

## 适用任务

| 你正在处理 | 可以这样开始 | 主要结果 |
| --- | --- | --- |
| 新功能或系统改动 | `用 UE PerfectWorld 先分析这个功能的现有实现和改动方案` | 项目证据、范围说明、S2 变更规格 |
| 已有报错或运行异常 | `用 UE PerfectWorld 根据这段日志排查根因，先不要改文件` | 根因分析、证据链、尚缺的信息 |
| 明确实现或修复 | `用 UE PerfectWorld 修复这个问题，先查证并简述改动范围，再完成实现、可用验证和独立审查` | 有界改动、审查后修复、验证与复审记录 |
| 多模块协作任务 | `用多个子代理并行查证和分块实现，主代理持续推进，独立审查后修正并复审` | 明确分工、整合改动及最新版验证与审查证据 |
| 已有规格的实现 | `按这份 S2 落点表实现，并按要求记录验证` | 授权范围内的改动、自审与验证记录 |
| 已有代码或补丁审查 | `用 UE PerfectWorld 审查当前 diff，按风险列出问题` | 分级审查发现与复验建议 |
| C++ 与蓝图协作 | `确认这个行为由 C++、蓝图还是两者共同负责，再分析改动` | 所有权、资产引用和交接约束 |
| 开发文档或交接 | `根据本次已完成改动整理 UE 开发文档` | 与实际改动和验证情况一致的交接文档 |

这些示例是自然语言入口，不是必须逐字使用的命令。任务涉及项目变更时，S0-S6 所需证据仍须覆盖，但检查点可以按任务规模合并，并在同一授权轮次连续完成。

## 快速上手

在已安装 Codex CLI 的环境中添加 marketplace 并安装插件：

```bash
codex plugin marketplace add 91pao/PerfectWorld
codex plugin add ue-perfectworld@perfectworld
codex plugin list
```

更新已安装版本：

```bash
codex plugin marketplace upgrade perfectworld
codex plugin add ue-perfectworld@perfectworld
codex plugin list
```

安装或更新后重启 Codex，或新开一个对话以加载技能。首次配置时可以运行 `ue-setup`：它会将 Codex 用户配置中的子代理并发上限默认设为 12 并核验，同时检查当前工作区及其父目录中的 `.uproject` 和可选 RAG 工具；它不会创建索引或修改项目。只要求“检查配置”时保持只读。插件安装本身不执行配置写入，已保存的设置与当前会话实际容量会分别报告。

```text
用 ue-setup 初始化 UE PerfectWorld，子代理上限设为 12。
```

安装完成后，在包含 UE 项目的工作区中直接描述任务即可。例如：

```text
用 UE PerfectWorld 帮我分析这个交互功能。
先确认现有 C++ 和蓝图分别负责什么，给出证据和变更规格，等我批准后再实现。
```

这个示例明确要求先规划，因此保持只读。需要直接修复时可以这样开始：

```text
用 UE PerfectWorld 修复这个交互功能的重复触发问题。
先核实现有调用链并简述改动范围，优先复用、配置或局部修复，
将可分离的查证、实现和验证交给多个子代理，主代理持续推进关键路径。
每个文件保持单一写入者，整合后独立审查，范围内修正并复验、复审。
不要自动提交或推送。
```

<a id="stage-gates"></a>
## S0-S6 证据检查点

以项目变更为终点的任务覆盖 S0 到 S6 的证据要求。检查点可以简写、合并，并在同一轮授权内推进；它们不是七次强制审批。明确的实现或修复请求已经授权有界文件改动时，先说明紧凑范围和规格即可继续。用户只要求规划、诊断、审查或不改文件时，保持只读。

多子代理执行贯穿这些检查点：S1 的独立查证可以并行，S3 的分块实现保持单一写入者，S4/S5 对稳定部分交叠验证和审查，S6 由主代理整合交付证据。并行安排遵循实际依赖，不以阶段编号分配固定代理。

| 阶段 | 处理内容 | 关键产物与推进边界 |
| --- | --- | --- |
| **S0 需求接入** | 明确目标、范围、非目标和成功标准 | 紧凑理解卡；仅真实待决策事项需要用户澄清 |
| **S1 证据底座** | 对照当前项目文件和可信先例核实需求 | 证据矩阵；结论标明 `path:line` 或证据缺口 |
| **S2 变更规格** | 明确改动文件、落点、理由及不改动范围 | 紧凑清单；当前实现或修复授权已覆盖时连续推进，新增范围再确认 |
| **S3 实现** | 按已授权范围小步修改并自审 | 改动集、自审记录；可接着完成已授权的验证 |
| **S4 验证** | 先列探针和预期结果，再执行可用验证 | 如实记录已通过、未运行和受限项目 |
| **S5 独立评审** | 检查需求符合性、项目一致性、生命周期和过度设计 | 对最新整合版本审查；范围内修复后复验、复审，未解决的 P1/P2 阻断完成声明 |
| **S6 交付** | 整理所需文档、验证证据和交付边界 | 对账检查点证据；不自动提交或推送，额外操作按各自授权执行 |

## 技能一览

| 技能 | 适用场景 | 工作边界 |
| --- | --- | --- |
| `ue-investigate` | 已有报错、日志或可复现故障 | 只读定位；不把诊断自动扩展成修复 |
| `ue-draft` | 方案、变更规格或实现范围仍需澄清 | 只读；输出 S0-S2 所需内容 |
| `ue-implement` | 明确的实现或修复请求，或已授权的 S2 规格 | 紧凑规格后只改授权范围；完成可用验证、独立评审与范围内修复复审 |
| `ue-review` | 审查已有 diff、补丁或已应用改动 | 只审查，不修改文件 |
| `ue-blueprint` | 蓝图资产、编辑器配置或 C++/蓝图交接 | 按需协作；由主工作流负责规划、实现或审查 |
| `ue-dev-doc` | 一次改动完成后需要开发或交接文档 | 依据真实改动和验证记录，不推测补写 |
| `ue-setup` | 初始化或检查插件配置、工作区与可选工具 | 初始化默认设置子代理上限 12 并核验；只检查时只读，不配置 RAG、不改项目 |

## 工作边界

- **先有项目证据，再给结论。** 项目相关判断要回到源码、配置或资产引用核实；找不到就说明缺口。
- **明确执行请求可授权有界改动。** 先说明紧凑范围与规格，再连续完成；规划、诊断、审查和不改文件请求保持只读，真实待决策或范围扩张再确认。
- **生产代码保持保守。** 优先复用、配置或局部修复；新增机制需要现有能力不足的证据，不把局部任务扩成框架改造。
- **多子代理协作是执行模块。** 主代理持续推进关键路径，子代理按真实容量承担有界工作；每个文件或资产保持单一写入者，整合后审查最新版本。
- **验证结果不夸大。** 未运行的编译、PIE、自动化测试或打包验证会明确标为未验证。
- **修复后重新验证与审查。** 实现任务内有界处理审查发现；单独审查保持只读，不把旧版本的通过结论沿用到最新改动。
- **额外操作按各自授权执行。** 文件编辑授权不自动包含构建、外部写入或版本控制操作，不自动提交或推送。
- **UE 项目按用户授权处理。** 不因插件安装而扫描无关目录、修改工程设置或执行完整构建。

## RAG（可选）

UE PerfectWorld 不附带 RAG 服务、索引器或向量数据库。只有当前 Codex 环境另行提供 `ue_rag_*` 工具时，技能才会使用它们辅助发现候选文件。

- RAG 结果用于查找线索，不作为代码、蓝图、生命周期、联网行为或清理逻辑的最终证据。
- 候选内容仍需通过当前项目文件直接核实。
- 没有 RAG 工具时，直接使用 `rg` 和源码读取；不会假称检索过索引。
